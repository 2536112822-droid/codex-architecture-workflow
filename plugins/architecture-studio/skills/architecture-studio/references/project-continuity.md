# Resume an existing design project

Use when a task continues a project, refers to a prior design/task, or needs shared decisions across deliverables. This is a focused recovery method, not a requirement to read all history or create a new memory system.

## Find and recover only what the current work needs

1. Identify the actual project and requested stage/object. Read its AGENTS.md pointer and existing continuity/progress entry. If starting outside the project, resolve the project from the available project/task list or known saved path first; do not assume the current directory is the intended project. Read only the relevant branch and necessary shared constraints.
2. Recover: intended outcome, adopted design basis, decisions still in force, superseded alternatives, open questions, current saved deliverable and its evidence. Preserve scope such as one-year versus ten-year, conceptual versus measured, group versus individual. An unrelated subproject's contract does not control all stages.
3. Check the relevant source files exist and match the recorded subject/version. Verify live document identity before writing. An old path that disappeared is a path problem until checked: search the known delivery folder, compare size/hash or application identity with the recorded evidence, and record a verified rename without rewriting historical receipts. Do not choose by newest modification time or the word “final” alone.
4. Where a consequential decision is missing or conflicting, retrieve the original user message, course/source requirement, reviewed image, or actual artifact that supports that specific claim. Use task IDs and bounded read_thread calls with pagination; do not dump tool outputs or image/base64 payloads. If the task tool fails or omits needed inherited history, inspect the exact local session's text messages in a bounded range, record the fallback source and read coverage, and follow fork ancestry when relevant. An empty fork log does not prove no prior work occurred.
5. Resolve only the conflicts that affect the current work. Reuse confirmed facts and decisions; ask once for a material unresolved choice only after available evidence has been checked. State the resumed basis briefly, without asking the user to reconfirm every prior decision. Do not start a guessed replacement scheme merely because a summary lacks detail.

## Keep meaning separate from recency

- A user decision records the original message location and applicable stage/object. New user corrections replace only the relevant earlier decision; retain its replacement link.
- A source requirement records its document/version/page, and whether it has actually been checked. Teacher feedback is attributed advice unless adopted or established as a course requirement. The user's design preference does not itself establish a physical, legal or technical fact.
- A candidate or assistant-selected implementation can exist in a model without being a user-approved design. Saved-file validation proves only its stated checks, not final aesthetic acceptance.
- An unresolved condition stays unresolved until supported evidence or a user decision resolves the relevant question. Silence, generic praise of an earlier version, and an assistant's completion message cannot promote it.
- Summary/memory/index entries are discovery aids. Resolve conflicts against claim-appropriate original evidence. A newer assistant summary cannot override an older still-valid user decision; file recency cannot waive a source requirement.

## One small maintained entry point

Use the existing authorized project record. If none exists, propose a fixed location under the user's save policy and prepare in task staging until that location is chosen. A short project AGENTS.md can point to a compact context file; keep actual project decisions out of global skills. A `.architecture/CONTEXT.md` file is suitable when no more specific record already exists. A database, vector index, nightly chat dump or automatic summarizer is not required.

Capture only information that affects continuing work: project identity/scope, current milestone and verification date, current artifact links, important decisions with status/scope/evidence, explicit replaced items and open questions, and the next useful action. Inline source locators suffice; add a separate source index only when it keeps the entry small. Preserve the original task title when naming it. Do not copy full conversations.

Keep one current status and next-action section. Replace completed setup to-dos with their result/source link, and remove repeated method explanations or historical QA narration from the entry when already retained in linked progress/evidence. Preserve decision/requirement IDs, artifact identity and unresolved conditions; shortening an entry does not authorize deleting original records. In a long entry, read its headings/routing and the relevant scope before expanding into unrelated branches. File/character reduction is an observation, not measured quota savings.

Update at a confirmed design choice, substantive correction, review result or delivery. Record the scope and original reply when marking a decision accepted; mark an output delivered without asserting approval. Check for another task's newer edits before writing the shared entry and merge relevant changes instead of overwriting it wholesale. Retain unresolved issues and provenance, update only affected branches, and keep one writer for the record.

After setup, verify the entry is discoverable from the actual task starting directories. A non-Git folder may load only its current-directory AGENTS.md; if necessary, use tiny relative pointers in the project's existing starting subfolders rather than duplicating the context or changing global configuration. Check actual retrieval from a fresh context as well as instruction loading. Neither test guarantees future recall, design quality or quota savings.

## Close a stage so that work can resume

At a meaningful stage end or handoff, update the existing entry even if no feedback arrives. Keep a short milestone: date and stage/subject, what was actually completed and where the current editable results are, the adopted decisions and their basis, checks performed and their limits, unresolved or deferred items, and the next useful action. Link the existing progress/source receipts for detail; do not copy them into a second journal, create empty forms, or summarize every chat turn.

Say what is ending: an exploration stage, a technical delivery, a design decision, or the whole agreed scope. Preserve outstanding requirements outside that stage. A completed stage can coexist with a pending broader outcome or a clearly excluded deliverable; it cannot claim its own unperformed required checks as done. Silence does not keep an otherwise complete stage open, but also does not approve a design. Ask only for decisions needed to continue dependent work, not for compulsory feedback or another save confirmation.

Keep the current milestone and live next actions at the entry point. Retain older decisions/checks in their original records, linked by subject/version; record replacement or reopening when relevant. Before updating, read the current record and merge another task's relevant changes. Follow existing save/retention rules for deliverables and temporary files; a closeout note does not grant authority to overwrite sources or delete unresolved candidates.

## Turn real feedback into a checked improvement

Use these steps proportionately for substantive feedback or an observed issue. A straightforward correction can be one short note and the appropriate check; do not require a report, database, category form or new process rule for every comment.

1. **Locate the issue.** Link the actual feedback/observation, author, affected project/stage/object, and the version that was reviewed. Identify the intended result and observed difference, with adequate evidence. If feedback concerns an older PDF/image/model, compare it with the current affected part before editing; an already fixed issue may need the right output delivered, not another model change. Ask a targeted question only if the missing distinction changes the next action.
2. **Understand the cause.** Separate an execution defect, a changed/new requirement, an evidence gap, a design preference/tradeoff, or a tool/delivery limitation as appropriate; these may coexist. Separate supported causes from hypotheses. Read the smallest useful original material or reproduce the relevant behavior. Do not blame a person/tool or invent a root cause from a screenshot alone. A justified local repair may proceed while a broader cause remains unresolved; say which question is still open.
3. **Check the scope.** Examine whether the same failure mechanism is permitted by other relevant stages, handoffs, or standalone professional entry points. One well-supported mechanism can justify a common repair without waiting for repetition; one project's aesthetic preference does not become a universal restriction. Consider any relevant area, including requirements, research/evidence, design, calculations, spatial/technical feasibility, making/use/maintenance, collaboration, tool execution, communication, editability, versioning, or time/quota/rework. This list is illustrative, not exhaustive or mandatory. Keep useful practices when supported; do not manufacture negative feedback.
4. **Repair at the right level.** Reuse project decisions for a local design choice, specialist methods for execution, and shared workflow rules for a demonstrated common gap. A problem can need both local and shared changes. Prefer fixing an existing rule or handoff to adding parallel machinery. Apply authorized routine corrections; take consequential design choices back to the existing discussion node with a concrete proposal. Follow [project contract](project-contract.md) to update only affected derivatives and checks. Current-project feedback can be applied under current authority; writing new learning/preferences to a long-term aesthetic library remains subject to that library's explicit selection rules.
5. **Verify and retain the right status.** Tie the check to the reported problem: actual file/geometry/use/visual behavior when that is the claim, instruction loading and a bounded retrieval/scenario check when the change is a workflow instruction. Compare against the relevant earlier failure and avoid breaking still-valid constraints. A rule edit or a simulated scenario does not prove better models, user acceptance, speed or quota savings. Keep implemented-but-unverified effects open with the specific subject and next useful trigger/check. Only mark the reported issue resolved with adequate evidence; explicit withdrawal/replacement is recorded as such, not as a successful fix.
6. **Resume or reopen.** Update the same issue when related feedback arrives, preserving what was changed, checked and still uncertain. Use a stable short issue ID only when it helps connect several rounds. If the issue recurs, reopen it and examine why the earlier repair/check failed; do not erase the old evidence or repeat the same change without new reasoning. A missing reply is not acceptance. Continue independent completed work; late feedback does not invalidate the whole project.

A compact existing-record entry may be: `feedback/source → reviewed subject/version and expected result → supported cause or open hypothesis → applicable scope and actual change → check/result → unresolved effect and next action`. These are prompts for useful information, not required schema keys. Link instead of duplicating an existing decision, artifact or check. No automatic polling, scheduled review or new memory store is implied by recording a later trigger.
