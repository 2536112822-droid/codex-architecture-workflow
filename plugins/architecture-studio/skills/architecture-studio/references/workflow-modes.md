# Workflow modes

Read only the matching mode. These are tool paths within the current design stage, not authority to complete every later stage. For a broader scheme, use the stage outcomes and early coordination in [brief to package](brief-to-package.md); honor established design discussion nodes and requested deliverables.

## Reference image to editable model and render

1. Inspect the original image; identify scale anchors, visible planes, openings, roof logic, material boundaries, camera, and occluded regions.
2. Record uncertain or hidden geometry as inference. Use the pre-model reference preparation in [brief to package](brief-to-package.md) if the adopted design lacks important detail; check complementary views for consistency without requiring a generated set. If no reliable scale source can be recovered, ask for one before dimension-critical modeling; labelled conceptual exploration may continue independently.
3. Produce a structured building plan with stable IDs and explicit units. Validate it before writing.
4. Apply the plan once in the selected native model tool (SketchUp or Rhino), inspect affected dimensions and semantic elements, then capture the orthographic and perspective views needed to verify the requested geometry. Reuse existing views only if the state they prove is unchanged.
5. Compare the relevant captures to the adopted references. Match camera/projection for direct fidelity comparisons when possible; otherwise state the qualitative limits and use actual geometry for dimensions. Patch only affected IDs, retaining any consequential unresolved design choice for discussion.
6. Generate presentation imagery only when it serves the requested deliverable and the existing authorization. A verified native capture may be sufficient. When generating from it, preserve camera, massing, primary openings, floor count, and roof outline; keep the user's model/route constraints and label the result as presentation-only.

## Site and brief to coordinated scheme

For a brief-led package, read [brief to package](brief-to-package.md). Use only the parts needed for the requested deliverables.

1. Read the relevant brief and attachments, preserving requirement locations and missing information. Verify location, study extent, true site boundary when available, and data dates.
2. Reuse valid site analysis and fill only consequential gaps. Convert supported findings into explicit design constraints or opportunities; link conclusions to data or image evidence.
3. Resolve consequential design choices with a plan, section, massing study, or comparison that tests the key assumption before adding detail. Record the adopted reasoning and remaining uncertainty. Follow an already clear direction directly; branch alternatives from shared evidence with distinct option IDs only when useful.
4. At the appropriate depth, coordinate the significant programme, spatial, structural/environmental and delivery constraints using [brief to package](brief-to-package.md). For the adopted branch, develop a shared level/grid/element specification, build in the chosen native tool and derive requested drawings from the same checked source. Different design phases/candidates may retain their own scoped baselines; do not impose a false single base or jump from a chosen image straight into a full technical package.
5. When requested, derive colored plans and area/indicator calculations from the current checked geometry, using the scope and traceability rules in brief to package.
6. Reconcile discrepancies and affected revisions in the project contract before issuing drawings or presentation boards.

## Text brief to editable CAD or model

1. Convert prose into a concise brief: units, envelope, levels, grid, components, openings, materials, views, tolerances, and deliverables.
2. Validate numerical consistency and list unresolved design choices. When the request also requires coordinated colored plans, indicators, or several deliverable types, use [brief to package](brief-to-package.md) for those outputs.
3. Generate a dry-run change set, then apply it atomically when supported.
4. Inspect bounding boxes, counts, clearances, levels, openings, and topology; capture a clean snapshot.
5. If a snapshot reveals interference or hierarchy errors, change the source parameters/specification and regenerate or patch. Do not manually hide the symptom.
6. Deliver editable source/specification plus requested exchange and viewing formats.

## Modify an existing project

1. Inspect the actual open document/model and compare its identity and revision to the contract. Establish and verify a recoverable working copy before changing an important original, or continue from this task's already verified working copy.
2. Express the request as a minimal patch against stable IDs.
3. Dry-run or validate the patch, apply it once, and verify both numeric state and captured views.
4. Identify affected drawings, colored plans, calculations, renders, and presentation sheets. Mark obsolete derivatives and checks using [project contract](project-contract.md); refresh only what the change invalidates.
5. Save and verify the updated working copy and update its artifact links. Keep revisions needed during comparison; handle final delivery and intermediate revisions under the current global save and retention policy. Reuse this task's specified or confirmed location and ask only for missing necessary decisions.
